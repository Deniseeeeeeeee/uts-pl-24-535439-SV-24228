PERTEMUAN 10
LOGGING TERSTRUKTUR & HEALTH CHECK

Log terstruktur tingkat INFO ditambahkan pada method store di MovieController, tepat setelah Movie::create berhasil menyimpan data. Konteks log berisi hasil LogContext::actor (user_id, ip, method, dan path), action movie.store, movie_id, fields, dan reason. Yang dicatat pada fields hanya nama kolom, bukan isinya. Alur simpan data dipilih karena operasi ini mengubah isi database. Log tersebut menjadi jejak audit tentang siapa menambahkan data, data mana yang ditambahkan, dan kapan. Log yang sama juga ditambahkan pada update, yang mencatat changed_fields, dan pada destroy.

Log tingkat ERROR untuk kegagalan koneksi database ditempatkan di app/Exceptions/Handler.php melalui callback reportable untuk QueryException dan PDOException. Jika causedByLostConnection bernilai benar, dicatat pesan “Gagal terhubung ke database” dengan component database dan reason berupa pesan PDO asli. Pesan QueryException sengaja tidak dipakai karena memuat SQL beserta nilai binding, misalnya email saat login. Alur ini dipilih karena kegagalan koneksi database membuat seluruh API gagal (HTTP 500) sehingga harus segera terlihat. Pada berkas yang sama, method invalidJson menulis log WARNING ketika validasi gagal. Log itu hanya memuat failed_fields dan rules_failed tanpa nilai input. Validasi gagal dipilih karena lonjakannya pada /api/login dapat menandakan percobaan brute force, sedangkan lonjakan pada /api/movies dapat menandakan kesalahan di sisi klien.

Endpoint GET /health dibuat pada HealthController. Pemeriksaan database menjalankan DB::select('SELECT 1') di dalam blok try/catch. Jika gagal, exception ditangkap, log ERROR dengan action health.check_database ditulis beserta latency_ms, lalu koneksi dibuang dengan DB::purge() agar pemeriksaan berikutnya membuat koneksi baru. Balasannya berupa status fail dengan pesan umum tanpa detail teknis. Pemeriksaan cache dilakukan dengan cara serupa, yaitu Cache::put lalu Cache::get dengan nilai acak. Endpoint membalas 200 bila semua komponen sehat dan 503 beserta daftar failed bila ada yang gagal. Route /health didaftarkan tanpa middleware session maupun auth sehingga tetap dapat menjawab ketika database mati.

Service app pada compose.yaml diberi healthcheck yang menjalankan curl -fsS ke http://localhost/health dengan interval 10s, timeout 10s, retries 3, dan start_period 40s. Opsi -f membuat curl keluar dengan kode non-zero saat /health membalas 503, sehingga Docker menandai container sebagai unhealthy. Paket curl ditambahkan ke Dockerfile backend agar perintah ini tersedia di dalam image. Lookup DNS ke host db yang sudah dimatikan sempat memakan sekitar 15 detik. Karena itu ditambahkan dns_opt timeout:1 dan attempts:1 serta DB_CONNECT_TIMEOUT 3 detik, yang memangkasnya menjadi sekitar 5 detik, dan batas waktu curl ditetapkan 8 detik. Service frontend memakai healthcheck wget, sedangkan db memakai mysqladmin ping.

Pembatasan ukuran log didefinisikan sekali dalam blok x-logging sebagai YAML anchor dengan driver json-file, max-size 10m, dan max-file 3. Blok ini dipakai oleh ketiga service melalui logging: *default-logging. Dengan konfigurasi tersebut Docker merotasi berkas log setiap kali mencapai 10 MB dan hanya menyimpan tiga berkas terakhir, sehingga log tiap service paling besar sekitar 30 MB dan tidak memenuhi disk host. Pada environment service app juga ditetapkan LOG_CHANNEL=stderr dan LOG_STDERR_FORMATTER=Monolog\Formatter\JsonFormatter agar log Laravel keluar ke stderr dalam format JSON.

Skenario pengujian dijalankan dengan skrip bukti/skenario.ps1, yang menyimpan output setiap langkah ke folder bukti/. Setelah docker compose up -d --build, perintah docker compose ps menampilkan ketiga service, yaitu app, db, dan frontend, dengan status Up (healthy). Status healthy pada app menunjukkan bahwa healthcheck berhasil memanggil /health di dalam container dan mendapat balasan sukses.

Perintah printenv di dalam container app menampilkan LOG_CHANNEL bernilai stderr dengan formatter JsonFormatter. Folder storage/logs kosong, dan berkas error.log milik Apache merupakan symlink ke /dev/stderr. Hasil ini membuktikan tidak ada log yang ditulis ke berkas di dalam container; seluruh log keluar melalui stderr dan dapat dibaca dengan docker compose logs. Image backend memakai php:8.2-apache (mod_php), bukan php-fpm. Pada mod_php, output php://stderr langsung menjadi stderr container, sedangkan php-fpm memerlukan pengaturan catch_workers_output = yes. Selanjutnya, docker inspect pada .HostConfig.LogConfig ketiga container menampilkan Type json-file dengan max-file 3 dan max-size 10m. Artinya pembatasan ukuran log benar-benar aktif, tidak hanya tertulis di compose.yaml.

Dalam keadaan sehat, curl -i http://localhost:8000/health membalas HTTP/1.1 200 OK dengan Content-Type application/json. Body balasan berisi status ok beserta hasil tiap komponen: database ok dengan latency 9,06 ms, dan cache ok dengan driver file serta latency 3,06 ms. Balasan ini menunjukkan kedua komponen benar-benar diperiksa, tidak hanya mengembalikan teks tetap.

Ketiga jenis log dipicu dengan mengirim request ke API. Login dengan email tidak valid dan password kosong menghasilkan HTTP 422 dan log WARNING berisi user_id null, ip 172.18.0.1, action POST api/login, serta failed_fields email dan password, tanpa mencatat nilai keduanya. Pengiriman data film tidak valid setelah login menghasilkan WARNING dengan user_id 1 dan failed_fields title, release_year, dan rating. Penyimpanan film baru menghasilkan HTTP 201 dan log INFO “Film baru disimpan” dengan movie_id 11, lalu pengubahan rating menghasilkan INFO “Film diperbarui” dengan changed_fields rating. Setiap log memuat siapa pelakunya (user_id dan ip), aksi yang dilakukan (action, method, dan path), serta sebabnya (reason). Token login hanya disimpan di variabel skrip dan tidak muncul di log.

Database kemudian dimatikan dengan docker compose stop db. Service app berubah menjadi unhealthy setelah sekitar 28 detik, sesuai konfigurasi tiga kali gagal berturut-turut (retries 3) dengan interval 10 detik. Output docker compose ps -a menampilkan db berstatus Exited dan app berstatus Up (unhealthy). Frontend tetap healthy karena hanya menyajikan berkas statis. Request GET /api/movies yang dikirim saat database mati dibalas HTTP 500.

Saat database mati, curl -i http://localhost:8000/health tetap mendapat jawaban, yaitu HTTP/1.1 503 Service Unavailable. Body balasan berisi status fail, komponen database fail dengan pesan “Tidak dapat terhubung ke database”, cache tetap ok, dan failed berisi [“database”]. Endpoint tidak crash karena exception koneksi ditangkap, dan balasan menyebutkan dengan tepat komponen mana yang gagal.

Output docker compose logs app selama database mati menampilkan dua sumber log ERROR. Yang pertama adalah “Health check: gagal terhubung ke database” dari healthcheck Docker (ip 127.0.0.1) dengan action health.check_database, reason getaddrinfo for db failed, dan latency sekitar 5.000 ms. Yang kedua adalah “Gagal terhubung ke database” dari request GET /api/movies (ip 172.18.0.1, action movies.index) yang dicatat oleh Handler. Kedua log tidak memuat query SQL maupun data pengguna.

Database dinyalakan kembali dengan docker compose start db. Database menjadi healthy dalam sekitar 7 detik, dan app ikut kembali healthy tanpa perlu di-restart karena pemeriksaan berikutnya membuat koneksi baru. Pemanggilan /health pun kembali membalas 200 OK. Rangkaian sehat, unhealthy, lalu kembali healthy ini membuktikan bahwa healthcheck bekerja dua arah.
